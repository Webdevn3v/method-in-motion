What Is a Bug?
LESSON 01 · FREE
01 / 05

Bugs Are Normal

Every programmer -- from beginners to professionals -- writes code with bugs. A bug is anything in your code that makes it behave differently than you intended. The goal isn't to write perfect code the first time. The goal is to find and fix bugs fast.

02 / 05

The Word "Bug" Is 80 Years Old

In 1947, engineer Grace Hopper found an actual moth stuck in a computer relay, causing it to malfunction. The team taped the moth into their log and wrote "First actual case of bug being found." The word stuck. Today, bugs are everywhere -- but they're always solvable.

03 / 05

Three Types of Bugs

Not all bugs look the same. There are three main types to know:

Syntax errors -- the code is written incorrectly. Missing a bracket, misspelling a keyword. The browser can't even run it.

Runtime errors -- the code starts running but crashes midway. Calling a function that doesn't exist. Using a variable before it's defined.

Logic errors -- the code runs fine but produces the wrong result. The hardest type to find because nothing crashes -- it just does the wrong thing.

04 / 05

Debugging Is a Skill

Debugging is not random guessing. It's a systematic process: understand what should happen, observe what actually happens, form a hypothesis about why, test it, fix it, and verify the fix. Good debuggers are calm, curious, and methodical.

05 / 05

The Console Is Your Best Friend

console.log() is the most basic debugging tool. Print the value of variables at different points in your code to see what's actually happening versus what you think is happening. When in doubt, log it out.

let total = 0; for (let i = 0; i < 5; i++) { total += i; console.log("i =", i, "total =", total); } // See what's happening at every step

Reading Errors
LESSON 02 · SPARKS+
01 / 05

Error Messages Are Information

Most beginners panic when they see an error message. Don't. An error message is the computer telling you exactly what went wrong. Learning to read them is one of the most valuable skills in programming. The message is not an attack -- it's a clue.

02 / 05

Anatomy of an Error Message

Most JavaScript errors have three parts: the error type, the message, and the location (file and line number). Read all three before doing anything else.

ReferenceError: x is not defined at myFunction (script.js:12) at onClick (script.js:24) // Type: ReferenceError // Message: x is not defined // Location: script.js, line 12
03 / 05

Common Error Types

ReferenceError -- you used a variable that hasn't been declared yet, or is out of scope.

TypeError -- you tried to do something with the wrong type of value. Calling a non-function, reading a property of null or undefined.

SyntaxError -- the code structure is invalid. Missing bracket, extra comma, bad keyword placement.

RangeError -- a value is outside its allowed range. Infinite recursion, invalid array length.

04 / 05

The Call Stack

Error messages often include a call stack -- a list of functions that were running when the error occurred. Read it from top to bottom. The top is where the crash happened. Below that are the functions that called it. This tells you how the code got to the error.

// Call stack reads top to bottom // crash happened in calculateTotal // which was called by processOrder // which was called by handleSubmit at calculateTotal (app.js:45) at processOrder (app.js:22) at handleSubmit (app.js:8)
05 / 05

The Browser DevTools Console

Every browser has built-in developer tools. In Chrome, press F12 or right-click and choose Inspect, then click the Console tab. This is where all JavaScript errors appear -- in red, with the line number, clickable to go straight to the code. Open it every time you build something.

Logic Tracing
LESSON 03 · BUILDERS+
01 / 05

What Is Logic Tracing?

Logic tracing is running code in your head -- or on paper -- step by step. You become the computer. You track every variable, every condition, every loop iteration, and write down what changes. It reveals logic errors that no error message will ever tell you about.

02 / 05

Tracing a Loop

To trace a loop, track the value of every variable at every iteration. Create a simple table: columns for each variable, rows for each step. This makes the pattern visible and impossible to miss.

let x = 1; let result = 0; while (x <= 4) { result += x; x++; } // Trace table: // x=1, result=0+1=1 // x=2, result=1+2=3 // x=3, result=3+3=6 // x=4, result=6+4=10 // x=5, condition false, loop ends // Final result: 10
03 / 05

Off-By-One Errors

The most common logic error in loops is the off-by-one error -- the loop runs one time too many or one time too few. This usually comes from using < vs <=, or starting at 0 vs 1. Always trace the first and last iteration carefully.

// Intended: print 1 through 5 for (let i = 1; i < 5; i++) { // BUG: misses 5 console.log(i); } // Fix: for (let i = 1; i <= 5; i++) { // correct console.log(i); }
04 / 05

Tracing Conditionals

When tracing an if/else chain, work through each condition with the actual values. Don't assume -- evaluate. Write out if (score >= 70) with the real number and check: is 65 >= 70? No. Which branch runs? The else. Follow the actual path the code takes.

05 / 05

Rubber Duck Debugging

Explaining your code out loud -- to a rubber duck, a friend, or nobody -- forces you to slow down and say exactly what each line does. Often the moment you start explaining, you catch the bug yourself. The act of forming words makes the logic visible in a new way.

Debug Challenge
LESSON 04 · CODERS
01 / 04

Advanced Debugging Strategies

Beyond console.log and reading errors, experienced debuggers use a set of mental strategies. Divide and conquer: narrow the problem by commenting out half the code and seeing if the bug persists. Minimal reproduction: strip the code down to the smallest version that still shows the bug.

02 / 04

try / catch -- Catching Errors Gracefully

Sometimes you expect code might fail. A try/catch block lets you run risky code and handle any error without crashing the whole program. The try block runs, and if it throws an error, the catch block runs instead.

try { let result = riskyFunction(); console.log(result); } catch (err) { console.log("Caught an error: " + err.message); }
03 / 04

Defensive Programming

Defensive programming means writing code that anticipates problems before they happen. Check that values exist before using them. Validate inputs. Provide defaults. Don't trust that a function will always receive the right data -- check it.

// Without defense -- crashes if name is undefined console.log(name.toUpperCase()); // With defense -- safe if (name && typeof name === "string") { console.log(name.toUpperCase()); } else { console.log("No name provided"); }
04 / 04

The Debug Mindset

The best debuggers share one trait: they don't assume. They verify. They don't think "that part works" -- they prove it. Every assumption is a potential bug. When stuck, question everything you thought you knew about what the code was doing. The bug is always there -- you just haven't found it yet.
