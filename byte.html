A bug is just a mistake in code that makes it behave differently than expected. That's all it is. Not a disaster. Not proof that you don't belong. Just a clue that something needs adjusting.

The word "bug" actually comes from 1947, when a real moth got stuck inside a computer and caused it to malfunction. The engineers taped it into their logbook and wrote "first actual case of bug being found." The term stuck forever.

Today, bugs are everywhere — in apps, websites, games, even spaceships. Every coder deals with them. The difference between a beginner and an expert isn't that experts don't get bugs. It's that experts know how to find them.

That's what Byte teaches. Not how to avoid bugs — how to hunt them.

📚
Key Terms
Bug
An error or flaw in code that causes it to behave in an unexpected or unintended way.
Example: A button that's supposed to turn blue turns red instead — that's a bug.
Debugging
The process of finding, analyzing, and fixing bugs in code. One of the most important skills in all of programming.
Example: Reading an error message and tracing it back to the line of code that caused it.
Error Message
A message from the computer or browser telling you something went wrong and usually pointing to where.
Example: "TypeError: cannot read property of undefined" — scary looking, but always fixable.
Syntax Error
A bug caused by incorrect spelling or structure in your code — like a typo in a language the computer doesn't understand.
Example: Writing </h1 instead of </h1> — a missing bracket breaks everything.
Logic Error
A bug where the code runs without crashing but produces the wrong result because the instructions are incorrect.
Example: Code that's supposed to add two numbers but subtracts them instead.

Reading Error Messages

Error messages look scary. They're not. They're the most helpful thing a computer can say to you — once you know how to read them.

◈

"The first time I saw a red error screen, I thought I broke the internet. Byte laughed. Then she showed me exactly what it was saying — and it made perfect sense."

Error messages are the computer's way of asking for help. They're not insults. They're clues. Every error message has three things: a type (what kind of error), a message (what went wrong), and a location (where in the code it happened).

Once you understand the structure of an error message, you can fix most bugs in under a minute. The error is already telling you where to look. You just have to listen.

The three most common types: SyntaxError means you typed something wrong. TypeError means you used something the wrong way. ReferenceError means you called something that doesn't exist yet.

📚
Key Terms
SyntaxError
The code is written incorrectly — wrong spelling, missing brackets, bad punctuation. The computer can't even read it.
Example: SyntaxError: Unexpected token — usually a missing comma, bracket, or quote mark.
TypeError
You tried to use something in a way that doesn't make sense for what it is — like trying to call a number as if it were a function.
Example: TypeError: undefined is not a function.
ReferenceError
You used a name that the computer doesn't recognize — usually because it was spelled wrong or doesn't exist yet.
Example: ReferenceError: myVariable is not defined.
Console
A tool in the browser where error messages appear. You can open it by right-clicking a webpage and selecting "Inspect," then clicking "Console."
Example: Byte lives in the console. That's where all the clues are.

Lesson 03 · Builders+

Logic Tracing

Sometimes there's no error message — the code just does the wrong thing. Logic tracing is how you find the bug anyway.

◈
Builders · Coders
This lesson is for Builders and up
Upgrade to unlock Lesson 3 — where you learn to think through code step by step like a real debugger.
📖
Read · 3 min

"Logic tracing is just playing detective. You read the code like a story, step by step, and ask: what is actually happening here versus what should be happening?"

Logic errors are the trickiest kind of bug because the computer doesn't tell you anything is wrong. The code runs. It just produces the wrong result. To find these bugs, you have to trace through the code yourself — like following footprints.

Logic tracing means reading each line of code and mentally tracking what the computer would do. You follow the values, watch them change, and look for the moment where something diverges from what you intended.

The most useful tool for this? console.log(). It lets you print any value to the console at any point in your code so you can see exactly what the computer is working with.

📚
Key Terms
Logic Tracing
Reading code line by line and mentally following what happens to each value — like watching a story unfold step by step.
console.log()
A JavaScript command that prints a value to the browser console. The most common debugging tool in existence.
Example: console.log(myScore) — prints whatever myScore is at that moment.
Variable
A named container that stores a value. When tracing logic, you track how variables change as the code runs.
Example: let score = 10 — score holds the value 10.
Expected vs Actual
The core of debugging. What did you expect the code to do? What did it actually do? The gap between those two things is where the bug lives.
⚡
See It Live · Trace the Logic

Watch Byte trace through code with a logic error. Can you spot it before she does?

// Goal: add 5 to a score and display it
let score = 10;
let bonus = 5;
score = score - bonus; // ← bug is here
console.log(score);
 
// Output: 5 (expected: 15)
◈ Byte's Trace: Line 2: score starts as 10
Line 3: bonus is 5
Line 4: score = 10 minus 5 = 5 ← bug! should be + not -
Line 5: console.log prints 5, but we expected 15

Fix: change - to + on line 4.

Debug Challenge

Everything comes together here. Real broken code. Real bugs. Your job is to find them, name them, and fix them.

"This is the real test. Not a quiz — actual broken code. Your tools: everything you've learned. Your goal: find it, name it, fix it."

You've learned what bugs are. You've learned how to read error messages. You've learned how to trace logic. Now you put it all together in a real debug challenge.

A good debugger doesn't panic. They slow down, read carefully, and ask three questions: What is this code trying to do? What is it actually doing? Where does it go wrong?

Answer those three questions and you'll find every bug. Every single time.

📚
Key Terms
Debugging Process
A systematic approach to finding and fixing bugs: reproduce the problem, read the error, trace the logic, form a hypothesis, test the fix.
Reproduce
Make the bug happen again on purpose. If you can reproduce it reliably, you can find it reliably.
Hypothesis
Your best guess about what caused the bug based on the clues. Good debuggers form a hypothesis before they start changing things.
Patch
The fix for a bug. A good patch solves the problem without creating new ones.
